# 明确日期行程的完整性契约

本契约适用于任何已给出明确日期、起止日期或行程天数的攻略，不区分信息来自用户口述、本地文件、表格、网页研究、旧版攻略或第三方资料。

## 1. 建立权威日期清单

在路线设计和 HTML 生成前，先建立日期清单，并记录日期依据：

- 用户当前消息明确给出的日期优先级最高；
- 其次使用用户指定的主资料、结构化表格或正式行程单；
- 再次使用现有攻略页面和公开研究资料；
- 不得用文件中间的空行、分页、合并单元格或章节分隔判断行程已经结束；必须读取到资料实际末尾并提取全部日期；
- 不同来源日期冲突时，先保留冲突并向用户说明；若用户要求直接继续，采用优先级最高的日期并把其余差异标记为待核验。

连续行程使用闭区间：`预计天数 = 结束日期 - 开始日期 + 1`。若用户明确只安排部分日期、跳过中转日或提供非连续日期，改用有序的明确日期列表，不自行补齐或删除。

日期清单至少包含：

| 字段 | 要求 |
| --- | --- |
| `date` | ISO 日期 `YYYY-MM-DD` |

若机票、住宿或旧版页面包含某个明确日期，但用户明确要求不把该日纳入逐日攻略，必须在 request、brief 与 content 的 `meta.dateExclusions` 中记录 `date`、`scope` 和用户决定的 `reason`。不得仅删除行程卡或依赖口头上下文；校验器会要求所有航班出发/抵达日期要么进入 `meta.dates`，要么有可审计的排除记录。
| `source` | 用户、本地资料、网页、旧版页面等依据 |
| `scope` | 主行程、抵达、离开、自由活动或明确排除 |
| `status` | 已安排、待补充、明确排除 |

## 2. 生成与修改门禁

- 日期清单中的每个“已安排”日期必须在逐日行程中出现且只出现一次，并保持时间顺序；抵达日、离开日、移动日和自由活动日也必须有行程卡，不得因内容少而省略。
- 页面首屏日期范围、逐日行程、交通、住宿、天气配置和返程日期必须使用同一日期基线。
- 增量修改前提取旧版页面日期；修改后逐项对比。新版缺少旧版日期或天数减少时立即停止覆盖，除非用户明确要求缩短、删除或排除对应日期。
- 更换模板、升级交互、迁移技能版本或重新生成 HTML 时，同样执行日期对账；“只改交互”不是跳过日期完整性检查的理由。
- 来源中存在明确日期但当天资料不足时，生成低密度行程卡并标注“待补充/待核验”，不得静默丢弃该日。

## 3. HTML 日期元数据

完整攻略在 `<body>` 或主页面根节点声明日期基线：

```html
<body data-guide-mode="full"
      data-trip-start="2026-09-25"
      data-trip-end="2026-10-06">
```

每个逐日行程卡声明唯一日期：

```html
<section class="day" id="day-0" data-itinerary-date="2026-09-25">
```

非连续日期使用：

```html
<body data-guide-mode="full"
      data-trip-date-policy="explicit-list"
      data-trip-dates="2026-09-25,2026-09-27,2026-09-28">
```

显示文本可本地化，但机器可读日期必须使用 ISO 格式。日期属性、卡片顺序和可见日期必须一致。

## 4. 自动验收与发布门禁

生成完整攻略时，把权威日期清单传给校验器：

```bash
node "<skill-root>/scripts/validate-guide-contract.js" guide.html --full \
  --expected-start=2026-09-25 --expected-end=2026-10-06
```

非连续日期使用：

```bash
node "<skill-root>/scripts/validate-guide-contract.js" guide.html --full \
  --expected-dates=2026-09-25,2026-09-27,2026-09-28
```

修改已有页面时同时传入旧版页面：

```bash
node "<skill-root>/scripts/validate-guide-contract.js" new.html \
  --expected-start=2026-09-25 --expected-end=2026-10-06 \
  --baseline-html=old.html
```

只有用户明确授权删除日期时才可增加 `--allow-date-removal`。该参数不代表可以忽略权威日期清单；新版仍须与新的用户确认范围一致。

验收必须输出并核对：起始日期、结束日期、预期天数、实际行程卡数量、缺失日期、重复日期、额外日期和相对旧版被删除的日期。任一异常均不得声明完成或发布。
