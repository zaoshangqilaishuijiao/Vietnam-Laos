# 内容模块与布局

完整攻略使用本文件统一内容模块、日期元数据和布局规范；局部修改只接入受影响组件。新建攻略由 `scripts/render-guide.js` 根据已通过的 `trip-data.json` 生成这些 DOM，模型不得在渲染阶段另写平行结构。页面 `<body>` 的 `data-guide-template-version` 必须等于 `scripts/shared-constants.js` 的 `PAGE_TEMPLATE_VERSION`，并使用 `data-guide-mode="full"`，并以空格分隔的 `data-guide-features` 声明条件功能，例如 `arrival exchange weather-refresh source-index day-tabs day-map day-navigation calendar-export expense-tracker`。共享外壳样式固定读取 `assets/guide-shell.css`；普通攻略不得附加目的地专属布局 CSS。

## 内容模块

主章节的 DOM 名称、顺序、固定标题、必选状态和导航属性以 [module-registry.json](module-registry.json) 为机器侧唯一真相源。`arrival` 仅在实际跨越中国大陆边境或发生国际/地区出入境时启用；其他业务说明写在本文件，不另建平行章节清单。

### 行程日期元数据

完整攻略在 `<body>` 或主页面根节点声明 `data-trip-start="YYYY-MM-DD"` 与 `data-trip-end="YYYY-MM-DD"`；非连续日期改用 `data-trip-date-policy="explicit-list"` 和逗号分隔的 `data-trip-dates`。每个 `.day` 行程卡必须声明唯一的 `data-itinerary-date="YYYY-MM-DD"`，并与可见日期、DOM 顺序和导航日期菜单一致。详细规则以 [date-coverage-contract.md](date-coverage-contract.md) 为准。

页面日期元数据只用于机器校验，不得替代生成前建立的权威日期清单。完整验收必须从用户或主资料取得预期日期，并通过校验器参数传入。

### 图片封面（固定模板）

新攻略使用本地目的地实景图作为首屏，不再生成独立纯文字标题页。封面 DOM 和视觉层级固定，目的地只能改变内容和图片：

1. 顶部页眉左侧为英文手册标识，右侧只放“当前主题名＋色环”的透明玻璃主题入口；不再重复目的地名称，也不放正文导航或“查看行程”按钮。
2. 中部只展示固定英文标识 `ITINERARY`、编辑短标题和一句话路线摘要。标题使用衬线字体并左对齐；目的地、日期、天数和人数不在中部重复展示。
3. 底部页脚下沉且只显示日期、目的地与天数三项事实信息。事实只从 `meta.dates`、`meta.destination` 与 `days[]` 计算；不显示图片来源、图片说明或其他封面补充文字。图片本身必须是随产物交付的安全相对路径。

`meta.hero.cover` 只包含 `src/alt`；不得生成 `credit`、`creditUrl`、`showCredit` 或 `showResume`。图片使用 `object-fit: cover`，桌面默认焦点约在中央46%；深色双层遮罩保证标题对比度，不靠给文字添加大色块救场。封面宽度始终占满页面，高度严格按当前可见视口使用 `100dvh`，并以 `100svh/100vh` 兼容移动端地址栏与旧浏览器；窄屏通过重排底部事实信息适配，不让正文进入首屏。宽屏依靠横向裁切、窄屏依靠纵向裁切保持满版，不使用固定像素高度，也不在封面外保留页面底色白边。

`meta.hero.title` 与 `meta.hero.subtitle` 是新攻略必填的原创编辑文案：

- 标题独立于 `meta.title` 和目的地列表，优先使用四个汉字，以“核心体验意象＋季节、时间或旅程气质”形成可辨识的封面题名；四字不能自然成立时允许更短或更长的精炼标题，不为凑字虚构事实。
- 标题从最终路线中提取真正反复出现或构成主线的体验，不逐个罗列城市，也不重复“某国之旅、旅行攻略”等已在页眉和全局信息出现的内容。
- 摘要使用一个完整句子，按实际行程顺序写出起点体验、关键地域或交通过渡、主要中段与最终收束，并在有用户依据时体现节奏、同行人或偏好；不堆砌所有停靠点。
- 标题和摘要只能重写已确认的行程事实，属于攻略编辑文案；不得直接摘录网站、拼接来源标题、把营销语当事实，或为押韵新增天气、景观和体验判断。

`meta.hero` 不定义目的地短评或全局事实字段，生成阶段不得创建这些内容；页面始终由模板输出 `ITINERARY`。封面底部固定呈现由数据计算出的日期、目的地与天数，不展示人数、泛化核验提醒或自由文案。旧 `kicker`、`footerNote` 及入口字段只为历史数据读取兼容，不能改变当前封面。

封面排印使用固定三层字号阶梯和左侧阅读轴，目的地不得另写专属字号覆盖：

- `ITINERARY` 是低权重眉题：11px、700 字重、1.3 行高、约 `0.2em` 字距；只承担类型标识，不与标题争夺焦点。
- 中文编辑标题是封面唯一主焦点：桌面使用 `clamp(56px, 8vw, 112px)`、700 字重、0.92 行高和约 `-0.07em` 字距，最大行宽 10em；手机使用 `clamp(34px, 10.8vw, 46px)`、0.96 行高和约 `-0.055em` 字距。标题优先单行，确需换行时最多两行，不能通过继续缩小到正文级字号容纳长文案。
- 一句话路线摘要为第二层：桌面 17px、1.9 行高、最大宽度 650px；手机 15px、约 1.72 行高。摘要左对齐并保持稳定起点，不居中排长句。
- 页眉和页脚为第三层：约 11–12px，依靠字重、明度和字距区分，不增加新的相近字号。
- 标题区保持左侧安全区与足够负空间；封面图片主体不得与标题重叠。桌面和手机都必须保持“眉题 → 标题 → 摘要”的阅读顺序，不能为了填满画面恢复事实行、短评或把各层平均放大。

`meta.theme` 可从 `rainforest/coast/terracotta/ink/burgundy/midnight` 中调整整页主题，省略时默认使用 `coast` 海岸蓝。自然森林与山野可选雨林绿，暖阳古城与地中海可选暖陶土，建筑博物馆与克制城市线可选墨色，美食葡萄酒与深秋路线可选勃艮第，夜景或冷调都市可选午夜紫；最终以封面照片的主色和明度关系为准，避免机械按国家选择。六套主题必须完整定义 `page/page-soft/deep/surface-dark/surface-dark-2/surface-dark-3/on-light/on-light-muted/on-dark/on-dark-muted/line-light/line-dark/action/accent` 语义角色；旧 `primary-50…900` 只能由这些角色派生供现有组件兼容，不能重新成为主题真相源。主题只改变颜色关系，不改变封面、卡片、表格或交互结构。

主题入口点击后打开右上角小型非模态调色盘，不生成全屏遮罩、不锁定页面滚动，也不覆盖正文。入口色环使用当前主题的浅色外圈与主操作色内芯，不能使用 `accent` 暖色代替主题色。调色盘两列展示六套主题的色点、名称与用途短语；点击空白区域、关闭按钮或 `Escape` 关闭。手机端保持视口内边距，极窄屏才降为单列。

组件不得直接写封面专属色值：深底、浅色主文字、弱化文字、暖色强调和遮罩分别使用 `--guide-cover-deep`、`--guide-on-dark`、`--guide-on-dark-muted`、`--guide-accent` 及由主题令牌生成的 `color-mix()`。封面始终保持“深背景＋浅文字＋低饱和辅助＋小面积暖色强调”的明度骨架；切换主题时封面、正文、按钮和状态色同步变化。旧 `showLinks/stages/budgetLabel/highlights` 仅作读取兼容，不能恢复旧首屏入口或布局。

### 主章节标题

每个启用正文模块的首个 `<h2>` 必须使用 `module-registry.json` 中的 `title`；首屏标题、模块说明、卡片 `<h3>`、标签与其他副标题可按目的地和内容自由编写。

### 现场探索、图片与具名换汇

- `route-map` 章节只呈现路线文字站点，逐日行程的 `#itinerary-explore` 承载唯一动态地图实例，复用同一排日期 Tab。新攻略按 [附近逛逛策略](nearby-explore.md) 在 `nearbyDays[]` 记录逐日状态与候选，引用现有 recommendations/venueSuggestions 的 ID。隐藏日不生成空面板，全部隐藏时不生成开关；逐日策略以 `application/json[data-nearby-policy]` 随页供契约校验。不复制地点事实，不改预定清单或正式时间线。旧 `explorationSegments[]` 仅保留兼容。
- `dayRoadRoutes[]` 保存每个旅行日按正式停靠顺序核实的驾车道路几何，不存密钥和实时路况。页面不请求在线路线规划，无法核实道路时不画经纬度直线。当天地图使用浅色安静底图、主题主色道路与正式字母点位；附近候选只有开关开启后显示。交通时间仍在时间轴胶囊，不重复压在地图上；正常加载不显示成功调试文案。
- 新攻略使用 `features.nearbyExplore=true`，旧 `contextualExplore` 只作兼容。所有带地点的附近候选必须有 `image: {src,alt,sourceId}`；图片来源指向 `sources[]` 中已实际阅读的小红书笔记，来源写作者及长链。图片文件放在 `trip-data.json` 同级相对路径，渲染时复制到攻略目录；发布白名单从最终 HTML 图片引用自动导出，同一图片进入 GitHub 页面。已有旧数据未启用此能力时可继续渲染。
- 夜市商品放在当地体验推荐的 `productPicks[]`，每项有具体商品名、差异化理由、图片和来源；餐厅菜单/菜品放在 `venueSuggestions[].menuItems[]`，记录具体菜品与证据，不把无实测价格写成当前价格。
- `budget.exchangeChannels[]` 与预算表分开：比较视图以 1000 CNY 总支出为默认，可改金额；仅在汇率和固定/比例/当地币手续费都明确时计算净到手量，否则显示“数据不足，无法比较”。现场双向换算从牛哞菜单打开独立弹窗，由用户点击刷新获取中间价；预算正文不重复放置汇率卡，中间价不能替代具名渠道的观察报价。
- `arrivalDeparture.experiences[]` 只显示有可比条件的亲历记录，显示机场、航站楼、观察日期、时段、签证类型及实际排队/出机场耗时；未知项省略，不补一般性提醒。
- 到达/离开的 `arrival[]/departure[]` 只写实际节点、办理顺序和必要动作。`reason` / `riskAlternative` 是旧数据兼容的可选补充：只有存在已核实的差异化选择条件或明确触发的替代交通时才填写；“航班晚到所以首日只入住”“返程日安排市内缓冲”“如延误优先入住”及复述正文的解释一律省略，不生成空的“选择依据／异常时改走”标签。不得为了让卡片显得完整而每步都填两项。
- 适用的出入境单据使用 `arrivalDeparture.forms[]` 就地展示在对应的到达或离开流程下，而不是写成“提前填好表格”的泛泛提醒。每张单据卡说明名称、适用护照/签证/口岸条件、在哪里及何时提交、官方入口（如有），并按真实字段名逐项写具体填法（例如从护照、签证或订单的哪一栏抄录及格式）；来源必须包含已核实的主管机关原始资料。只写填法，不写旅客的真实姓名、证件号、住址或申报答案。没有需要填写的单据就不显示该区块；字段、适用性未核实的单据不放入网页。
- `arrivalDeparture.apps[]` 是到达/离开内的“当地常用 APP”，不新增主章节，也不复制逐日 A→B 的方式和耗时。只选本次目的地实际会用的打车、外卖、铁路/公交、共享电动车/自行车等应用，不按类别或数量凑卡；同一 APP 只建一条，`region` 说明适用国家/城市，跨地通用时写组合范围。统一在一张紧凑列表中展示：32px官方Logo、名称与弱化地区、用途与确会影响使用的 `notice`（如需当地手机号、付款方式限制）；行间用细分隔线，不重复地区大标题或为单个APP留半行空列。手机端说明移动到名称下方，保持正文可读与自然换行，不靠截断文字压缩高度。仅 APP 名称是复制按钮，使用可访问名称说明动作，不显示“复制名称”提示或下载入口。用途、条件、Logo 和行背景保持非交互内容，不放进复制按钮，也不显示复制下划线；名称触控区至少44px并支持键盘。`officialUrl` 仅在核实后保存在数据中，不渲染为按钮；`sourceIds` 指向运营方官方页面或由开发者发布的应用商店条目。Logo 使用安全相对路径并随攻略交付，不用外链热加载；无法核实 Logo 或具体用途的应用不进入列表。数组为空时不显示空区块，旧数据无 `apps[]` 继续可读。

### 机场落地三件套

到达部分使用 `arrivalDeparture.airportKits[]`，每组以从 0 开始的 `arrivalIndex` 锚定 `arrival[]` 的实际机场抵达节点，紧跟该节点显示；`airport` 与 `nextStop` 说明机场和本次酒店或下一站。仅限机场场景，多国／多机场分别研究，不套用其他机场资料。

固定研究 `sim` 电话卡、`exchange` 换汇、`transport` 前往下一站三类。每张卡使用一句简短 `lead` 给出建议，`facts[]` 按 `label/value/sourceIds` 分行承载可执行事实；动态报价、套餐、营业或班次观察使用 `observedAt` 标注日期。仅有会改变选择的条件才填 `condition`；`details` 只收纳额外有用的报价和使用差异，不复述已展示内容。每条事实必须引用实际读过的小红书笔记，记录作者、原帖与观察时间；建议、条件、详情由这些事实支持。官方资料可另行交叉核查，不能替代三件套的小红书研究。

- 电话卡：明确提前买还是机场买及原因；写出柜台／运营商、位置、覆盖本次天数的套餐、流量、币种与价格。有证据才写号码、短信、通话或激活差别，不把流量卡视为必然能收短信；提前购买需有具体产品或渠道依据。
- 换汇：区别具名银行柜台、商店与 ATM，提供位置、观察日期、报价方向和手续费；净到手与牌价分清，不把不同日期数值当作同日比价。是否先换少量现金结合买卡或交通付款条件。复用具名渠道事实，与预算保持一致，不用中间价冒充成交价。
- 前往下一站：围绕实际酒店／下一站给出叫车 APP、上车位置、支付方式与有依据的费用；公交地铁方便时给线路、购票点、票价、时段／班次及下车站或接驳。别处酒店车费不能当作本酒店报价；未核对末班或站点不能承诺晚到能坐或直达酒店。

只提供有用信息：不写“提前准备、注意安全、合理安排、看现场、先比价”等独立空话，不用“暂无资料／待核验”填卡。三类均需研究；未查到的字段在文字研究稿记录缺口，网页省略，不能为三列齐全编造或生成占位卡。无机场抵达或旧数据缺少本字段时不输出空区块。

布局沿用确认的演示：一处组标题与“机场 → 下一站”，按电话卡、换汇、交通排序；标题与编号、突出建议、对齐事实行、可选条件、原生 `details/summary` 和可选的底部补充阅读（无入选内容时不生成来源页脚）。容器至少 960px 时等宽并排（完整三件套三列），较窄时单列；不缩小正文或截断文字，不用长段落塞满卡片。颜色跟随主题变量，名称复制仍复用 APP 清单，不新增下载入口或独立交互控制器。

### 逐日信息、强度与备注

- 每张逐日卡必须以 `.day-overview-top` 输出统一摘要工具栏：日期在左，天气、当天地图和 `.day-intensity` 在右组成三个等高并排控件。三者使用相同字号、最小高度、圆角与横向内边距；天气是弱状态但保留外框。格式固定为"行程强度 `N.N 🌟`"，不使用冒号。评分范围 0–5、最小单位 0.5；页面保留结构化数据中的全部 🌟 强度提示，不改成轻松/适中/高强度等平行标签，也不由前端重新计算。窄屏时三控件同组下移整行，不另设“当天导航”入口。
- 同一时间线区块的 `activity + details[]` 只有一条时使用普通段落，不显示编号；有多条时使用有序列表，按 1、2、3 顺序显示。
- `notes[]` 全部进入 `.slot-notes` 黄色区域；底部 `.meta` 只承载交通方式、移动/停留耗时和路线断点，不纳入黄色备注。
- 地点地址只在该地点首次出现时显示，并作为 Google Maps 搜索链接；`links[]` 输出为可直接点击的新窗口网页链接，统一带 `noopener noreferrer`。
- 原始资料中与具体行程节点直接相关的停车表、路线图或经验截图，使用该条目的可选 `referenceImages[]` 就地展示，不汇总为页尾附件图库。页面显示紧凑缩略图、标题与用途说明，点击后复用统一图片预览；手机单列。经验截图仅作参考，动态规则与实时路线仍以官方信息和分段导航为准。
- 景点、体验和餐饮三个 `.recommendation-module` 保持固定，以保证攻略结构一致；某类没有有效推荐时允许列表为空，但不得生成“不适用项”“暂无推荐”或其他填充文字。分类整体备注是可选信息：只有整类推荐共享一项会改变执行动作的特殊条件时，才在列表后输出一条 `.recommendation-module-note`，标题固定为"整体备注："；没有有效内容时不输出备注标签和容器。第四组文化习俗不使用分类整体备注。

“当地体验”作为 `bookings` 后方相邻的独立导航模块，统一收纳景点、体验、餐饮、文创与文化习俗。每个地点使用与预定清单相同的 `.guide-action-card` 视觉骨架和响应式网格：标题与路线关系标签同排，推荐理由为正文，适合时段与耗时为弱化元数据，限制与替代执行合并为次级提示区；底部统一提供 `Google Maps ↗ → 小红书 ↗` 操作区。手机单列，容器达到 720px、980px、1240px 后依次为 2、3、4 列，最多四列。

签证、证件、安全和天气不另设内容模块，统一进入 `checklist`。跨境清单至少包含护照有效期、签证 / 入境许可、返程或续程材料、保险、紧急联系方式和官方安全提醒；境内行程不生成签证项。所有清单项必须是可执行动作，动态要求标注核验日期并以角标链接官方来源。天气区域在同一清单模块内呈现常年判断、刷新按钮、状态区和临近出发结果。

### 逐日推荐挂接（可选）

`recommendationPlacements[]` 仅引用已有 `venueSuggestions[].id` 或带稳定 `id` 的 `recommendations[]`，并锚定 `days[].items[].id`。它只在对应时间线节点后显示紧凑的“顺路提示”；每个挂接位 1–2 项，不新增浮层、日期切换、地图图层、预订状态或本地/协作存储。路线标签只能为真正顺路、附近、短绕路、需要绕路四档，不把编辑判断伪装成实时距离或导航事实。

顺路提示与预定清单允许投影同一候选项，但职责必须分离：顺路提示只显示“此时为何值得去、路线关系、简短用途”；`bookings` 中的候选店铺卡是官网、预约政策、特殊提醒与后续管理的唯一详情入口。每个时间线锚点内同一 `venueSuggestion.id` 只能出现一次；同一候选同时符合多个时段时，选择离锚点最近且语义最准确的位置；已是执行时间线条目或真实预订项目的地点不再以顺路提示重复推荐。候选店铺在顺路提示中必须提供一个明确的“查看候选详情”原生页内链接，目标为预定清单中同一 `venueSuggestion.id` 的稳定锚点；不得将整张卡片变成跳转区，也不得复制官网、预约政策或管理控件。无法在预定清单定位的普通 `recommendations[]` 不显示该链接。

### 当地体验四分组

当地体验主章节包含以下三类推荐及可选的文化习俗组，禁止另外建立目的地专属推荐章节。模块结构固定不等于文字必须填满：前三组没有有效条目时保留空列表，不生成空卡片、“不适用项”或说明性占位文字；文化习俗按其独立契约保留：

1. `景点指南`；
2. `当地体验`；
3. `餐饮指南`；
4. `文化习俗`。

前三组共用 `recommendations[]` 契约：每项必须有稳定 `id`，并填写 `reason`（为什么值得）、`travelerFit`（为什么适合本次同行人）、`timing`、`routeRelation`、`duration` 和 `reservation`；`limit` 与 `executionAdvice` 仅在确有差异化条件时填写。有可核验地点时引用 `placeId`；有官方页面时使用 `officialUrl`。理由必须说明目的地独特性和本次旅行适配性，不能只写“热门、值得、网红”。`travelerFit` 必须结合本次行程的具体取舍条件，至少说明时间窗口、同行人偏好、体力、天气风险或需要替换的既有安排之一，并让读者据此决定“加入、替换或放弃”；禁止使用“主线完成后仍有时间”“补充目的地辨识度”“适合想深度体验的旅行者”等不改变决策的套话。一般购票或预约要求只写入 `reservation`，不再复制为提示；限制或执行建议必须提供具体触发条件、对本行程的影响和明确动作，无法做到时省略字段。

### 补充说明的信息价值门槛

同一价值门槛适用于正文、黄色备注、折叠详情和所有辅助说明。删除免责或任务转交式文字，如“机场计划到达节点为个人缓冲，不代替航司值机／登机要求”“或按实际情况改出租车”“酒店接驳班次另行落实”。有用内容应给已核实的具体班次、预约时点、上车位置、费用或明确接不上时的替代方案；未核实的内容留在文字研究稿，不转成网页提醒。不要把泛化说明藏进详情来规避省略规则。

风险、替代、备注、提示、核验、限制和现场执行都属于可选补充信息。只有满足至少一项时才生成：与当前日期或路线发生明确冲突；包含可核验的截止时间、阈值或窗口；存在地点或运营方特有规则；存在已核实的停运、施工、罢工或季节关闭；给出有名称的替代方案及时间、费用或预约差异；与同行人的体力、无障碍或明确偏好形成具体取舍。推荐表达为“具体触发条件 → 对当前行程的影响 → 应采取的动作”。

不得用旅行常识填充字段，包括“下雨带伞”“出门前看天气”“注意时间”“合理安排”“灵活调整”“以现场为准”“排队时错峰”“下雨改室内”“景点需要买票”等。不能确认有实质信息时直接留空，不写“不适用”“暂无风险”或“待核验”，渲染器必须连同空标签和空容器一起省略。明确赶不上、明确闭馆或明确不满足规则时可以提示，并必须写出导致判断的时间或规则依据。

第四组使用 `localKnowledge[]`，按适用性选择 `文化特点`、`会客礼仪`、`文化禁忌`，每类最多一张；全不适用时空数组并以 meta.cultureNote 说明，网页不显示空模块。字段仍为 `category/title/guidance/action/dayNumbers/placeIds/sourceIds`，其中日期与地点数组用于兼容旧数据，新卡片默认留空且不再投影到逐日时间线。每张卡必须基于可靠来源说明会改变游客现场行为的差异，并给出具体建议；不写民族性格概括、猎奇标签或无法核验的禁忌。需要完成或确认的动作仍进入核验清单，文化背景不得复制成清单条目。

`venueSuggestions[]` 进入第三组“餐饮指南”，保留 `booking-venue-<id>` 稳定锚点和官网、地图、小红书操作。若同一 `placeId` 同时存在于餐饮 `recommendations[]` 与 `venueSuggestions[]`，只渲染信息更完整的候选场所卡，计数也只记一次。

### 全页自适应密度与防拥挤

- 章节纵向内边距控制在 16–24px，一级章节标题不额外叠加顶部默认外边距；卡片首尾内容不额外留空。通过减少外边距与内边距提升密度，不缩小正文或移动端触控区。
- 预订卡片的标题与状态用双列网格同排，详情跨两列；长标题自然换行。卡片上下内边距桌面12px、手机10px，卡片间距8px；空链接段不占高度。
- 每日卡片以细主题色竖条、低强度阴影区分日期面板；强度 4–5、3、0–2 分别使用错误、提醒、成功语义色，文字与星级始终保留。时间线用主题色时间列与低对比 hover 背景提升扫描效率；悬停仅补充反馈，不作为手机端状态提示。

- 本规则覆盖首屏、到达 / 离开、地图说明、逐日行程、交通、预算、推荐、核验清单、资料来源及其内部组件；所有高信息密度卡片、表单、工具栏与操作区默认单列纵向排列，不要为视觉平衡强行并排。
- 需要在宽屏并排时使用共享 `.guide-adaptive-pair`，并显式标记 `data-guide-wide-layout="verified"`。该布局仅在容器宽度达到 960px 后启用两列，其他宽度自动回到单列。
- 标记 `verified` 前，必须实测卡片标题、按钮、输入框、结果、单位和说明均不截断、不重叠；390px、412px 与中等桌面宽度均不得把交互内容压缩到难以阅读。任一项不成立就保持单列。
- 宽表格只允许在自身滚动容器内横向滚动；卡片、网格子项和表单控件必须 `min-width:0; max-width:100%`，不得制造页面级横向溢出。
- 交通和预算等静态表格标记 `data-mobile-cards`：桌面保留表格，窄屏按 `td[data-label]` 转为纵向信息卡。天气表数据密集且需横向比较，继续保留容器内横向滚动，不强制转卡片。

### 数据表格

交通表、预算表、天气表（含运行时生成的地点表）共用同一套表格规范，样式唯一定义在 `travel-guide-interactions.css` 的"数据表格"段，渲染器与共享脚本不得另写平行的表格样式。

- **容器**：统一使用 `.table-wrap`（静态表）或 `.guide-weather-table-wrap`（天气卡内嵌表），表现为 1px `--guide-line` 边框、`--guide-radius-md` 圆角、白底、仅容器内横向滚动。预算备注等表后内容放在容器外，不得混入滚动框。
- **单元格**：统一 `padding: var(--guide-table-cell-padding)`（10px 12px）、左对齐、顶端对齐；表头使用 `--guide-table-header-bg` 底色、加粗、轻微字距、不换行；表体偶数行使用低对比主题浅底，末行去底线；行 hover 使用 `--guide-table-row-hover`（仅 `hover: hover` 设备）。
- **宽度**：基础 `min-width: var(--guide-table-min-width)`（680px）；天气地点表等 6 列以上密集表格使用 720px。数值列（天气 `.metric`）使用 `font-variant-numeric: tabular-nums`。
- **语义**：合计 / 小计行使用 `<th>` 承担行头语义并自动获得强调底色；长文本列（天气 `.weather` / `.key`）允许换行。
- 可调令牌：`--guide-table-min-width`、`--guide-table-cell-padding`、`--guide-table-header-bg`、`--guide-table-row-hover`，目的地只覆盖变量，不改结构。

封面不生成 `data-resume-day`、`hero-execution-link` 或图片来源节点；进入逐日行程统一使用正文快速导航和右下角组合工具。文化卡片按适用性出现，每类最多一张，空模块不渲染。
