# 逐日“附近逛逛”策略与兼容契约

用于新建攻略、补齐附近候选或升级此模块。候选是值得选择的地点，不是必须逐店完成的计划，也不局限于填补原行程空隙；用户可以据此调整原安排。地点事实复用 `places[]`，引用已有 `recommendations[]` / `venueSuggestions[]`；展示候选本身不自动改正式行程、住宿、交通选择、预定状态或 ICS。研究篇数、来源身份和动态事实核验仍按 [研究规则](research-and-sources.md) 执行。

## 价值优先，再说明安排上的取舍

1. 先依据当地特色、品质、独特性和用户兴趣选点，有证据说明为什么值得。顺路是加分项，不是入选门槛；同一目的地值得专程前往的店也可进入当天推荐，不要求每个候选在既定空闲窗口内去完。
2. 围绕当天确定会停留的城市、目的地、古城或已确认酒店研究，不围绕待定酒店编造位置。核对具体分店，不重复当天正式地点，不用相同店铺凑数；不以步行距离、绕路程度或原时间表已满直接排除有价值的地点。
3. 普通日选 **3–5 处**，真正交通日选 **1–3 处**，结合推荐质量与当天活动空间说明取舍，不按空闲分钟数机械分档。只有几乎全天持续移动、没有常规目的地活动窗口才判为 `transit`；半天航班/列车、换城不自动构成交通日，其余为 `ordinary`，不从 `days[].kind` 自动推断。
4. 时间、距离、营业和预约是安排提示，不是普遍入选条件。有依据时可在 `area` 写“顺路可去”及位置关系；值得专程去的说明理由与交通，无证据不造绕路分钟数。天气、预约或明显需要替换原活动时才提醒；无需每店都加标签或设计替换方案。晴天/雨天等互斥支线写清适用条件，不表达成全部连逛。保留已订航班、列车等硬节点提醒，不自动改动计划，不把推荐变成必去任务。
5. **22:00 后才完成抵达、接驳和入住**，或**12:00 前就须离开酒店/游玩区域**，可以不显示，边界时刻本身不强制隐藏。`hide-no-free-window` 只用于即使调整一般游览也没有目的地活动机会的实际情况，不能仅因行程排满、建议休息或资料不足而隐藏；不显示与交通日分类独立。
6. 可选记录不需调整原计划的**净自由窗口**作为安排参考；没有这种窗口仍可显示推荐，填 `freeWindows=[]` 并省略候选的 `windowIndex`。不得为通过校验清空正式条目时间、虚构窗口或承诺来得及。填写窗口时仍须扣除接驳、入住/退房、候机缓冲；航班落地/起飞时刻不是探店可用边界。

## 店铺与伴手礼
有明确购物或探店需求时，按目的地和兴趣设研究目标。以下为三天城市行程的全程参考量。

| 类别 | 全程参考量 | 怎样才算有得选 |
| --- | --- | --- |
| 特色产品、伴手礼 | 3–5 种具体产品 | 覆盖不同需求，例如轻便小礼物、实用布艺、工艺器物。每种至少有一个核实过的购买点。 |
| 特产店、设计店、手工艺店 | 4–6 家 | 各家有会影响选择的差异，例如款式更多、能看制作、适合最后一天补买。 |
| 咖啡店 | 3–4 家 | 覆盖顺路歇脚、特色饮品、值得为环境专程停留等不同用途。 |
| 其他特色店铺 | 1–3 家 | 按本次旅行兴趣补充，例如参赛行程可研究当地跑步装备专门店。 |

商品和到访地点分别计数，门店按地点去重。重点商品有两个核实过的购买点时，记录款式、用途及路段差异。缺少有依据的选择时先定向补查。表中数字用于研究，页面沿用逐日候选数量规则。

入选店铺沿用当天「附近逛逛」的原卡片。用 `shopPick` 写具体商品、款式、饮品或进店体验，用 `whyNow` 写适合哪种需求或与邻近店铺有何区别，用 `timing` 写会影响选择的营业、绕路或行程取舍。已排入正式行程的店在原条目补选购重点，候选卡可在文案里引用它做比较。地图、定位、导航、详情和原帖继续复用原入口。

有依据时用 `routeFit` 标明 `along_route`（顺路）、`same_area`（同片区）、`detour`（需专程）。顺路要结合当天路线与实际步行、换乘或过河条件判断。同片区无法确认顺路时按同片区展示。模板依次展示顺路、同片区、未分类、需专程，同组沿用原顺序。旧数据可省略两个字段并保留原卡片。

## 数据表示

新建或明确升级的攻略默认 `features.nearbyExplore=true`，`nearbyDays[]` 对每个行程日恰好一条；不显示日也保留记录。每条包含：

| 字段 | 约束 |
| --- | --- |
| `dayNumber` | 引用行程日，唯一；全数组覆盖完整行程。 |
| `status` | `show`、`hide-late-arrival`、`hide-early-departure`、`hide-no-free-window` 或 `research-pending`。 |
| `dayType` | `ordinary` / `transit`，与显示状态独立。 |
| `reason` | 说明类别与推荐取舍，或不显示的实际原因；不把行程排满等同于不值得推荐。 |
| `readyAt` / `leaveAt` | 可选的 `HH:MM`：完成抵达/接驳/入住，或必须离开活动区域的当地时间。晚到状态须 `readyAt > 22:00`；早离状态须 `leaveAt < 12:00`。 |
| `freeWindows[]` | 可为空，不作为显示资格。若填写则按时间排序、不重叠，每项含 `startTime/endTime`、`city`、已确定且有坐标的 `anchorPlaceId`、已扣除的 `bufferMinutes` 与说明依据的 `basis`。时间是目的地当天当地时间，不解析柔性 `timeText` 或跨时区推算。 |
| `candidates[]` | 显示日普通 3–5 / 交通 1–3；合理不显示日为 0，`freeWindows=[]`。每项含 `targetType/targetId/whyNow` 和安排提示 `timing`；`whyNow` 先说明价值与用户兴趣，`timing` 按需说明时段、预约或调整提醒，不承诺必能赶上。`area` 可选。`windowIndex` 可省略；填写时须引用真实窗口且城市一致，省略时仍须属于当天正式地点/住宿或日程所确定的城市。 |

`research-pending` 表示资料仍未核完，不能伪装成合理不显示；content 校验阻止其作为完整攻略渲染。研究阶段可保留此状态和缺口。新结构须具备状态、类别、理由和窗口数组（可为空），才能采用新数量规则。

填写的净自由窗口不得覆盖同城正式条目的确定 `startTime/endTime` 及其已记录的同城接驳；候选/已取消条目不当作固定占用。这是对“自由窗口”声明的核验，不是对推荐价值的筛选。没有合适窗口时省略窗口引用，不改正式时间字段。柔性 `timeText` 不解析为时钟，跨城市当地时间不直接相减，仍须人工核对交通与缓冲依据。

## 道路、开关与失效处理

- `dayRoadRoutes[]` 为可选增强，可以缺日、缺腿或为空。已有腿必须按正式停靠顺序形成子序列，核验折线与起终点；不得跳过正式节点或跨 `breakGroundRoute` 断点。缺段显示“未绘制/待核”，只画已核实道路，绝不画经纬度直线，也不在网页打开时规划路线。道路缺口不阻断附近候选。
- 单一日期 Tab 驱动一张共用地图；开关状态按日独立保留在本次页面会话。关闭时卡片与候选点同时隐藏；合理不显示日隐藏空开关/空面板并显示简洁原因，整篇功能保持启用。所有日期均不显示时不生成开关。
- 候选卡与地图点双向定位；跨日复用同一地点时只定位当前日的卡片。图片预览、来源链接、移动端小红书跳转沿用共享组件；图片加载失败显示替代文本，地图失败或拒绝定位时仍能阅读、看原帖和打开外部导航。图片授权不明时不能自动公开再发布，发布前换用有权使用的图片或仅保留原帖入口。
- 继续支持键盘、44px 触控目标、390/412px 无溢出、减少动效、六套主题与地图版权。地图和共享交互重复初始化复用实例，销毁后可重建。

## 旧数据与正式升级

- 没有新增字段的旧 JSON 继续可渲染；旧 `nearbyDays[]` 无 `status` 时沿用原 5–10 处兼容路径，不猜测交通日或改写数据。不能只填新字段又省略 `status`，以此混用数量规则。旧 `contextualExplore` / A→B 探索仍只保留兼容。
- 2.49 起显示日允许 `freeWindows=[]` 和不带 `windowIndex` 的候选；旧记录中真实且有效的窗口与索引继续使用，无需迁移。新规则不自动重排旧攻略、恢复隐藏日或修改日历；旧页面需从确认基线重新渲染才获得新文案。
- 旧攻略只升级附近逛逛时，必须提供相同 `meta.guideId` 的已确认 JSON 基线与变更白名单。未启用全量 `contextualExplore` 的基线中，与旧条目及其关联地点、来源完全一致的推荐可保留旧图片/地点信息；完全未改动的预算可保留原有换汇模块。兼容保留项在校验警告中逐项说明。新增或修改推荐、全部逐日候选仍检查图片、作者、原帖及坐标；没有基线、新攻略、启用全量 `contextualExplore` 均不适用此兼容。后续增量更新仍需传本次已确认基线，不能删除候选证据或借旧 ID 改写内容。[研究规则](research-and-sources.md) 的已读篇数硬门槛不变。
- 正式攻略从最近一次已确认 JSON 与正式 HTML 建立本地基线，声明变更白名单并证明内容连续性。试点注入页不能作为正式基线或共享模板；JSON 重新渲染后来源索引、计数、地图和卡片一致。模板升级不冻结旧 DOM，也不自动发布既有攻略。
- 改动后运行策略、schema、渲染、HTML 契约、地图双向交互与旧数据兼容测试，再按 [验收规则](verification.md) 全量回归和真实浏览器验证。HTTP 200、静态通过或测试中的地图替身都不能证明真实底图已验收。
